# NIST SP 800-115

## Technical Guide to Information Security Testing and Assessment

[[NIST-800-115.pdf]]

**NIST Special Publication 800-115**, _Technical Guide to Information Security Testing and Assessment_, is a guide published by the **National Institute of Standards and Technology (NIST)** for planning and conducting technical information security tests and assessments.

The guide is not a penetration testing playbook with a fixed sequence of commands. Instead, it provides a framework for deciding **what should be tested, how it should be tested, and how the results should be handled**. It is useful for penetration testers, security teams, system owners, and organisations that need a structured approach to evaluating their security posture.

The document focuses on technical testing and assessment activities that can be used to identify vulnerabilities, verify security controls, and determine whether systems are adequately protected.

## The Assessment Process

NIST SP 800-115 divides security testing into three broad activities:

**Planning → Execution → Post-Execution**

The exact tests performed can vary considerably depending on the environment. A small web application assessment and a large enterprise network assessment may require completely different techniques, but both can follow the same general process.

### Planning

Planning establishes the conditions under which testing will take place.

Before touching the target, the tester should understand the **objectives, scope, authorised systems, testing constraints, and expected outcomes**. This is particularly important when testing production environments, where an aggressive test can cause service disruption.

Planning can involve defining:

- Assessment objectives.
    
- Scope and target systems.
    
- Testing methods.
    
- Roles and responsibilities.
    
- Communication procedures.
    
- Rules and limitations.
    
- Resources and tools.
    
- Schedule and test windows.
    
- Reporting requirements.
    

A good plan should make it clear what the assessment is intended to achieve and what is outside its scope.

## Security Assessment Techniques

NIST SP 800-115 describes several types of technical assessment techniques. These can be broadly divided into **examination, interviewing, and testing**.

### Examination

Examination involves reviewing information without necessarily interacting directly with the target in an intrusive way.

Examples include reviewing:

- System configurations.
    
- Network diagrams.
    
- Documentation.
    
- Logs.
    
- Policies and procedures.
    
- Source code.
    
- Security architecture.
    
- Vulnerability scan results.
    

This can provide useful context before active testing begins and can reveal weaknesses that may not be visible from external testing alone.

### Interviewing

Interviewing involves obtaining information from people who understand the systems and processes being assessed.

System administrators, developers, security personnel, and other stakeholders may provide information about how systems are configured, how security controls operate, or how incidents are handled.

Interviewing is not a replacement for technical validation. Information obtained from personnel can be used to guide testing and can then be compared with the actual technical state of the environment.

### Testing

Testing involves actively interacting with systems to determine whether vulnerabilities or weaknesses actually exist.

This can include techniques such as:

- Network discovery.
    
- Port and service identification.
    
- Vulnerability scanning.
    
- Password testing.
    
- Web application testing.
    
- Wireless security testing.
    
- Penetration testing.
    
- Security control testing.
    

Testing should be selected according to the objectives and risk of the assessment. Not every test is appropriate for every environment.

## Network Discovery

One common part of a technical assessment is identifying systems and services within the target environment.

The tester may determine:

- Which hosts are reachable.
    
- Which ports are open.
    
- Which services are running.
    
- Which operating systems are being used.
    
- What versions of software are exposed.
    
- How systems are connected.
    

This information helps establish the attack surface and provides the basis for later vulnerability analysis.

Tools such as **Nmap** can assist with this process, but the methodology is more important than the individual tool. The tester needs to understand what information is being collected and why it matters.

## Vulnerability Scanning

Vulnerability scanning uses automated tools to identify potential security weaknesses.

A scanner can be useful for quickly examining large numbers of systems, but its results should not automatically be treated as confirmed vulnerabilities.

False positives, outdated information, unusual configurations, and environmental context can all affect scanner results. A professional assessment therefore requires **validation and analysis** rather than simply exporting scanner output into a report.

A useful workflow is:

**Scan → Review → Validate → Analyse → Report**

## Penetration Testing

Penetration testing goes beyond simply identifying possible vulnerabilities. It attempts to determine whether weaknesses can actually be exploited and what level of access or impact could result.

Depending on the scope, this may involve:

**Reconnaissance → Discovery → Vulnerability Analysis → Exploitation → Post-Exploitation**

The purpose is to provide evidence of real security impact while keeping the activity controlled and within the authorised scope.

For example, identifying an exposed service is useful, but demonstrating that the service allows unauthorised access provides much stronger evidence of risk.

## Rules of Engagement

Technical testing needs clear boundaries.

The **Rules of Engagement (RoE)** define how the assessment is expected to be performed. They can specify the systems that may be tested, permitted techniques, testing windows, communication channels, and actions that are prohibited.

This is particularly important when testing systems that support business-critical operations.

A tester should never assume that because a system is technically reachable, it is automatically authorised for testing. **Authorisation and scope determine what may be tested.**

## Post-Execution Activities

Once technical testing has finished, the results need to be analysed and documented.

Post-execution activities can include:

- Reviewing collected evidence.
    
- Analysing identified vulnerabilities.
    
- Determining security impact.
    
- Removing temporary test artefacts.
    
- Documenting findings.
    
- Preparing the assessment report.
    
- Communicating results to relevant stakeholders.
    

The assessment should leave the environment in an appropriate state and ensure that temporary accounts, files, payloads, or other artefacts created during testing are handled according to the engagement requirements.

## Reporting

The final report should turn technical observations into information that an organisation can act on.

A useful finding should explain:

- **What was found**
    
- **Where it was found**
    
- **How it was identified**
    
- **What evidence supports it**
    
- **What the potential impact is**
    
- **How the issue can be mitigated**
    

Technical details are important for the people responsible for remediation, while a clear description of business or operational impact helps decision-makers understand why the finding matters.

The goal is not to produce a list of tools or commands used during the assessment. The goal is to communicate the **security condition of the environment and the actions required to improve it**.

## NIST SP 800-115 in Practice

NIST SP 800-115 works well as a high-level guide for organising a technical security assessment.

For example, during a network assessment, a tester might start by defining the scope and objectives, perform network discovery, identify exposed services, analyse vulnerabilities, validate significant findings through controlled testing, and finally document the results.

The methodology can therefore be adapted to different environments rather than forcing every assessment into exactly the same workflow.

## NIST vs Other Frameworks

NIST SP 800-115 is not the only framework available, and the different approaches serve different purposes.

**PTES** is focused specifically on structuring penetration testing engagements and provides a clear penetration testing lifecycle.

**OWASP WSTG** is specialised for web application security testing.

**OSSTMM** provides a broader security testing methodology with its own concepts and approach to operational security testing.

**ISSAF** provides structured guidance for information systems security assessments.

**MITRE ATT&CK** is different from all of these: it is primarily a knowledge base for describing adversary tactics and techniques rather than a complete assessment methodology.

In practice, these resources can complement each other. A tester might use NIST SP 800-115 to structure an assessment, OWASP WSTG for detailed web testing, and MITRE ATT&CK to map relevant adversary techniques.

## Practical Mental Model

A simple way to remember the NIST approach is:

**Plan the assessment**  
→ Define objectives, scope, rules, and constraints.

**Conduct the assessment**  
→ Examine, interview, and technically test the environment.

**Analyse the results**  
→ Validate findings and determine their significance.

**Report the results**  
→ Provide evidence, impact, and remediation guidance.

**Improve security**  
→ Remediate weaknesses and, when appropriate, retest them.

NIST SP 800-115 is therefore less about a specific collection of hacking techniques and more about **performing technical security testing in a controlled, structured, and useful way**.
